The shared idea

A character is a tree of radicals

  • ~500 radicals and 12 layout operators (⿰ left-right, ⿱ top-bottom…) build every character.
  • Unicode writes the tree as a string, the IDS. Every paper reads the same file.

The benchmark

Train on m handwritten classes (500 to 2,755). Test on 1,000 classes never seen. Fewer training classes = harder.

0:40. 森, forest, is three trees: a tree on top of two trees side by side. Click: as a tree. Click: as a string, that's the IDS, and everybody uses it. Click: the benchmark everyone reports. Train on m classes, test on 1,000 unseen ones. Keep m in mind: small m is the hard case.

Predict it, encode it, or align with it

Building a code: HDE (2020), simplified
$\varphi(y)=\sum_{\text{radical } r} \alpha^{d_r}\, e_r \;+\; \lambda \sum_{\text{operator } s} \alpha^{d_s}\, e_s$

one dimension per radical / operator; $d$ = depth in the tree; $\alpha=\lambda=\tfrac12$

⿱0$\lambda\alpha^0 = 0.5$ to $e_{⿱}$

⿰1$\lambda\alpha^1 = 0.25$ to $e_{⿰}$
木, 木2$2\alpha^2 = 0.5$ to $e_{木}$

⇒ $\varphi(森)$: 木 = 1.0, ⿱ = 0.5, ⿰ = 0.25, every other dim 0.

HDE 2020 → CUE 2023 → HierCode 2025 → JRED 2025

$\hat y = \arg\max_{y\,\in\,\text{all classes}} \cos\big(f(x),\,\varphi(y)\big)$

train the image network $f$ on seen classes; unseen ones only need their $\varphi$.

The code is frozen before training. 呆 (口 over 木) and 杏 (木 over 口) get the same counts: only a tiny position term, in the 4th decimal, tells them apart.
0:50. Drop the decoder. Give each class a vector computed from its tree, regress the image onto it, take the nearest code. Walk the table: count each node, weighted by one half per level of depth. 森 gets 1.0 on 木. (The real HDE adds a tiny position term, which I dropped; removing it costs only 0.31 pt.) 呆 and 杏 are the same parts in a different order, and their codes differ in the fourth decimal.   • Same CLIP idea, but the "caption" is a picture of the character in a font, not its tree.
  • Works where no tree exists: Japanese kana never seen in training, rare variants.
Needs a font that draws every class. Fewer than 5 fonts cover all 97k characters, and a modern font is not the shape of a 17th-century woodblock.

On the next chart it is drawn dashed: each unseen class comes with a printed glyph the tree methods never see, so it is not a like-for-like comparison.

0:35. The obvious alternative: forget the tree, render each class in a font and match the image to the rendering. OpenCCD and PCSS do that. It even handles scripts with no decomposition, like kana. The catch: you need a font that has every glyph, and font shapes are not woodblock shapes. (My own test: adding an ink-to-font contrastive term to my encoder gave nothing, −0.8 pt top-1 font matching.)

Where my work fits

A learned embedding, used to fix a reader's mistakes

  • I train a contrastive glyph encoder, family 3's recipe on the image side.
  • Each glyph's nearest neighbours vote on its label: a graph over the whole book.
What the graph is for
  1. Detect errors: a glyph whose reading disagrees with its look-alikes.
  2. Catch hallucinations: the reader writes a plausible character that is not on the page.
  3. Expose model conventions: one reader writes the Taiwan form, another the Hong Kong form, of the same glyph.

Run on a real Qing-dynasty volume: 770 pages, no ground truth.

1:00. My thesis uses this literature from the other end: I don't need to name unseen characters, I need glyphs of the same character to land close together, and I use that to vote out OCR errors.
